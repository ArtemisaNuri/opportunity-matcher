# Workshop Notes

- **Date:** September 24, 2026
- **Attendees:** Joel, Artemisa, Gerti
- **Recording:** No link (iPhone recording)

## Executive Summary

The team scoped a new internal Internyl tool — an opportunity scoring and matching system — designed to help Joel decide which incoming client opportunities to pursue based on Internyl's actual capacity, budget fit, timeline, and sector restrictions at any given moment. The group walked through the full app in three layers: an opportunities table/list, a two-part opportunity detail screen (client-facing evaluation fields plus internal capacity/team data with several comparison charts), and a final AI-driven scoring module that assigns each opportunity a weighted score, a match category (e.g., Top Match, Queued Match, Deferred Match), and a written explanation. A recurring design principle emerged: keep the UI as simple as possible (e.g., using a single toggleable comparison chart instead of many separate charts) and lean on AI to auto-populate opportunity data from call transcripts/recordings rather than manual data entry. Several structural questions — exact score-to-category thresholds, the detailed "evaluation UI" for reviewing AI scoring, and the axis logic for the team-availability heatmap — were left unresolved and flagged as things to refine once the team starts using a working version.

## Full Summary

### 1. Purpose and Core Goal
- The tool's core purpose: **allocate resources to new (incoming) opportunities** by matching them against Internyl's current capacity and constraints.
- Framed as: a system that **scores opportunities** and matches them against Internyl's own operational state (team availability, project load) so Joel doesn't lose clients he could realistically deliver for in a good timeframe.
- Assumed opportunities enter the system early-stage — e.g., from website contact forms or initial client meetings/calls — not from deep-in-pipeline deals.
- Joel referenced having a small number of live opportunities at the time of discussion (the count was unclear in the recording — referenced as roughly "3" or "3–4") that could serve as real test cases for the system.
- Joel repeatedly framed this exercise as **scoping**: asking Artemisa and Gerti clarifying questions the way he would with his own clients, to understand what they were envisioning before build.

### 2. Screen 1 — Opportunities Table
- A main table/list view of all opportunities (rows), sortable.
- Clicking into a row opens the opportunity's detail screen.
- Discussed whether this should function like a lightweight CRM/board (e.g., similar to Notion-style tables) — confirmed yes, a structured table rather than a more complex "credentialed application"-type system.

### 3. Screen 2 — Opportunity Detail Screen (Part 1: Opportunity/Evaluation Fields)
Fields identified as needed on every opportunity for evaluation/matching purposes:
- **Restricted sectors** — e.g., Joel does not want to take on healthcare clients due to HIPAA compliance concerns, even though he noted he'd otherwise like to serve that sector and maintains a good relationship with at least one healthcare-adjacent contact.
- **Client's budget** — if too small, they won't take the work.
- **Timeline** — how much time the client needs/expects the project completed in.
- **Project size / cost to build** — distinct from the client's stated budget; this is Internyl's own estimated cost/effort to build it.
- **Project profile / details** — general descriptive details about the opportunity/project to aid evaluation.
- **Project stage/type** — a simplified 3-option classification:
  1. Full build, end-to-end
  2. QA only / picking up an existing project (a "recovery" project)
  3. Prototype
- These fields collectively make up the "opportunity/client" half of the detail screen, used for evaluation.

### 4. Screen 2 — Opportunity Detail Screen (Part 2: Internal Data / Capacity)
Internal data objects required to match against opportunities:
- **Team members and their capacity** (current hours/week, open hours/week).
- **Existing projects and their launch/milestone dates.**

Three visual components were designed for this half of the screen:

**a) Existing Projects Chart**
- A horizontal, Gantt/timeline-style chart showing all currently running projects, each in a different color, plotted over time.
- Purpose: quickly see where a new opportunity's timeline would overlap with existing project timelines (e.g., "this project starts in December and runs X long").
- Should support a couple of display options.

**b) Team Capacity Chart** (with toggle between three views)
1. **Show team by capacity** — table with team members as rows and columns for current hours/week and open hours/week (a simple "who has bandwidth right now" view).
2. **Show team grouped by project** — table grouped by project, showing which team members are assigned and their involvement, including team members not currently assigned to any project.
3. **Show team by capacity over time** — a heatmap-style view:
   - X-axis: time filter (3 months / 6 months / 12 months out)
   - Y-axis: team members
   - Cell color: darker = more available, lighter = less available
   - Tooltip: shows exact hours available
   - The exact axis logic (e.g., what "months" means on which axis, how filtering interacts with the grid) was debated at length and **not fully resolved** — the group acknowledged it may need to be refined once tested ("it doesn't have to be perfect... it'll surface a lot to us").
- The team briefly discussed adding a fully granular per-person weekly-hours editing interface but **decided against it for now** to avoid unnecessary complexity — the capacity charts were deemed sufficient.

**c) Project Comparison Chart**
- Rather than building many separate charts, the team designed **one combined, toggleable comparison chart** allowing the user to choose which project sets to compare on the same timeline:
  - Existing projects
  - Top-match opportunities
  - Queued opportunities
  - The opportunity currently being viewed
- Joel specifically praised this as a strong UX/simplification decision — consolidating what could have been "10 different charts" into one toggle-driven view.

### 5. Screen 3 — Scoring / AI Evaluation Section
- A dedicated section (below the opportunity + internal data sections) where the actual scoring happens.
- Trigger: a "Run" / "Score Now" button.
- Output of scoring:
  - A **weighted score**, calculated from the opportunity's data points evaluated against Internyl's internal state (team capacity, existing project load, etc.).
  - The score **deterministically maps to a match category** (see below).
  - A **brief written explanation** from the AI describing how the opportunity stacks up against Internyl's current internal data.
- This section was acknowledged as **not fully designed** — the group ran out of time to spec the detailed "evaluation UI" (how a user reviews, second-guesses, or overrides an AI-generated score). Decision: leave it mocked/static for now rather than build it out in this pass.

### 6. Scoring Categories and Thresholds (discussed, not fully finalized)
The group worked through category definitions iteratively and left some ambiguity in the exact cutoffs — captured here as best resolved from the discussion:
- **Top Match** — great fit AND team has current availability → can start/close immediately. Roughly 90%+ (numbers like 90–95% were floated but not locked in).
- **Queued Match** (also referred to as "Backup Match" during the discussion, with some back-and-forth on naming) — great fit, but no current team capacity → queued until a spot opens up. Rough range discussed was ~70–90%, though the group flagged uncertainty about whether an additional band (e.g., 80–90%) was needed here.
- **Deferred / lower-tier match** — some overlap with what Internyl does, but not ideal; only pursued if there's extra capacity. Loosely associated with a **50–70%** range ("average match").
- Below that range (implied, not explicitly labeled) would presumably not be pursued at all.
- **Action item / open question:** the exact score-to-category boundaries and final category names need to be locked down before or during build.

### 7. Data Entry — Auto-Population Concept
- Rather than manually filling in every opportunity field, the team discussed having **AI auto-populate the opportunity's row** in the table from source material such as:
  - A written description or notes doc, or
  - A sales call recording/transcript.
- Flow envisioned: raw transcript/description → AI model extracts and maps the data → populates the relevant fields (budget, timeline, sector, project size/cost, etc.) → row appears in the opportunities table → weighted scoring can then run.
- Manual editing of auto-populated rows would still be supported.

### 8. Design Philosophy Notes
- Joel repeatedly emphasized keeping the build **simple and UI-focused for this pass** — explicitly deferring backend/database architecture discussion.
- Preference for consolidating multiple potential views into single toggle-driven components (seen in both the Team Capacity Chart and the Project Comparison Chart) rather than proliferating separate screens/charts.

### 9. Open Items / Unresolved Threads
- No "evaluation UI" was designed — how a user reviews an AI-generated score/category/explanation in detail. Agreed to fake/mock this for now.
- Team Capacity heatmap axis logic (months vs. team members, and how the time filter interacts with the grid) was discussed extensively but not conclusively settled.
- Exact percentage thresholds and final naming for match categories (Top Match / Queued Match / Deferred Match, etc.) were not locked down.
- No explicit owners, deadlines, or next steps were assigned during the recorded portion of the meeting.
